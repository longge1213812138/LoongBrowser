# ADR-0010：用自实现的 Aero Snap 同时拿到分屏与玻璃常驻

- 状态：已采纳
- 日期：2026-10-19
- 取代：ADR-0007 的"不做 Snap"结论（其关于 WS_THICKFRAME 的实测结论仍然成立并已被复测确认）

## 背景

用户要求：**贴边分屏必须回来，玻璃常驻也不能丢，"不要做取舍，我全都要"**。
ADR-0007 当年为了玻璃放弃了 Snap，理由是系统 Snap 必须 `WS_THICKFRAME`。

## 复测：那条红线还在

用彩色条纹背板 + 饱和度判据重测四种边框形态（探针已随结论删除）：

| 配置 | 前台 sat | 失焦 sat |
| --- | --- | --- |
| None，无 WS_THICKFRAME | 46 | **46（玻璃存活）** |
| None + WS_THICKFRAME | 46 | **0** |
| Sizable（系统标题栏）+ WS_THICKFRAME | 46 | **0** |
| None + WS_THICKFRAME + WM_NCCALCSIZE 归零 | 46 | **0** |

并补测"能不能救"：

| 失焦后的补救 | sat |
| --- | --- |
| 重新 `GlassManager.Apply` | 0 |
| `Clear` → `Apply` → 强制整窗重绘 | 0 |
| 切回前台 | 46（自动恢复） |

结论：**只要样式里出现 WS_THICKFRAME，失焦时 Acrylic 必被 DWM 停用，且无法在失焦状态下救回**。
这与边框形态无关，换 `FormBorderStyle` 或抹掉非客户区都绕不过去。

同时验证了"系统 Snap 需不需要这一位"：不带 `WS_THICKFRAME` 的窗口，即使 `WM_NCHITTEST`
正确回答 `HTCAPTION`，把窗口拖到屏幕边缘也**不会**被吸附。所以"让系统做 Snap"这条路，与玻璃常驻确实互斥。

## 决策：自己实现 Snap 的可见行为

不碰 `WS_THICKFRAME`，把 Snap 的三条可见行为按 Windows 规范复刻（`src/SnapController.cs`）：

| 手势 | 行为 |
| --- | --- |
| 拖到左 / 右屏幕边缘（阈值 12px） | 落位为左 / 右半屏 |
| 拖到屏幕顶部 | 最大化 |
| 从最大化状态拖离 | 立刻还原成拖动前的大小，指针落在标题栏上 |
| 双击标题栏 | 最大化 / 还原 |

窗口尺寸仍由系统缩放循环驱动：`WM_NCHITTEST` 对四边四角回答 `HTLEFT/HTRIGHT/…`，
系统据此起缩放循环 —— 这条路**不需要** `WS_THICKFRAME`，所以玻璃安全。

## 验证

- 真实鼠标拖拽（`SendInput` + 真实光标）：
  拖到左边缘 → `L=0 W=1280 H=1392`（正好左半屏）；
  拖到右边缘 → `L=1280 W=1280 H=1392`（正好右半屏）；
  拖到顶部 → `L=0 T=0 W=2560 H=1440`（最大化）。
- **分屏且失焦时玻璃仍在**：sat = 44（同一个探针在 ADR-0007 的配置下测得 0）。
- 单元测试 `tests\run_snaptest.ps1`（19 项）：贴边判定、半屏矩形左右正好拼满、
  奇数宽度不留缝、从最大化拖离的还原几何。
- 端到端 `tests\run_snap_test.ps1`（12 项）：样式不含 `WS_THICKFRAME`、
  最大化铺满工作区不盖任务栏、还原回原位、玻璃已应用。

## 代价

- 松手瞬间没有系统那条吸附动画（位置是对的，只是没有 400ms 过渡）。
- 不支持"拖到边缘后继续拖到相邻显示器"这类跨屏细节，以及 Win11 的 Snap Layouts
  悬停面板（那由系统标题栏的最大化按钮触发，自绘标题栏拿不到）——
  需要时用 Win+方向键，这条系统快捷键对本窗口仍然有效。
- Snap 的几何规则由我们自己维护（半屏、顶部最大化）；Win11 的 1/3、1/4 分区未复刻。
